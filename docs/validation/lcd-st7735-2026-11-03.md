# ST7735 display bring-up — 2026-11-03

The connected 1.8-inch module is marked `DRIVER IC: ST7735` on its back and
`128*120` on its front PCB. No temperature probes were connected. The ESP32-S3
ran the pinned ESP-IDF v6.1 firmware with the ST7735 driver, 128 × 160 portrait
geometry, GPIO12/11/10/9/14 for SCLK/MOSI/CS/DC/RESET, and no firmware-controlled
backlight GPIO.

The first diagnostic image showed blue/green/red bars where red/green/blue were
expected, and stray pixels at the right edge. Setting RGB element order and a
controller RAM gap of x=2, y=1 produced the expected red/green/blue sequence;
the owner's follow-up photo showed all four TL/TR/BL/BR labels, the complete
border, and no obvious stray right-edge pixels. The 128 × 160 test frame fits
the visible panel despite the PCB marking. Exact active pixel counts and the
physical screen dimensions have not been independently measured.

A 30-second test-pattern smoke passed during Wi-Fi association and time sync:
no panic, healthy history, zero fabricated sensors, internal heap 91,375 bytes
after display initialization, and a 45,404-byte internal-heap minimum watermark.
The port successfully registered two 128 × 40 RGB565 buffers with DMA and PSRAM
allocation requested. A separate 15-second diagnostic smoke passed and recorded
seven LVGL flush-start to subsequent flush-wait-completion intervals from 4,786
to 23,460 microseconds. These are software transfer timing samples, including
rendering/scheduling overlap; they are not end-to-end optical refresh latency or
a long-duration load measurement.

The owner confirmed the LCD showed the correct local time after network time
synchronization. The board's Settings API reported `America/Los_Angeles`,
including after a USB-triggered restart. A first read immediately after reset
showed dashes; serial health logs showed synchronization within about six
seconds on the subsequent run. New installs now default to that timezone;
previously saved timezone selections remain intact.

An authenticated 90-second test temporarily selected Extended mode with
five-second Overview and Trends dwell, then restored the previous settings.
Seventeen logged transitions alternated correctly; representative transition
uptimes were 41,255 ms (Trends), 46,314 ms (Overview), 51,255 ms (Trends),
and 56,316 ms (Overview). Eighteen five-second health records were captured.
The owner confirmed that the Trends screen appeared during the cycle and
questioned whether its five small graphs would be readable. At the owner's
request the compact Trends view now shows one 120 × 75-pixel chart at a time,
rotating between installed sensors every five seconds of visible Trends time.
Headless tests use simulated history and confirm all five sensors receive a
turn. Actual-probe graph readability, alerts and the longer physical UI soak
remain separate checks.

The normal firmware with the larger rotating graph was subsequently built,
flashed, and passed a 15-second bare-board smoke with the LCD initialized,
healthy history, no fabricated probes and no panic. The clock remained
unsynchronized during that short run; earlier it synchronized and the owner
confirmed the displayed local time.

The owner reports VCC and BL connected and chose to defer voltage measurements.
Their wiring destinations, supply/backlight electrical ratings, current and
GPIO15 compatibility remain unverified. This pattern does not verify sensor
readings, alert appearance, Extended-mode dwell, or a long soak.

## Addendum 2026-11-04 — idle Wi-Fi memory capture (T04-03)

The normal ST7735 image (not simulation; no `CONFIG_MONITOR_LCD_TEST_PATTERN`)
was built with the pinned ESP-IDF v6.1 toolchain and flashed to `/dev/ttyACM0`
with a plain `idf.py flash`; no erase or partition-table change was made. The
application region was already identical to the flashed image, so that step only
verified it. `tools/device_smoke.py` then captured 180 seconds of serial output
from the reset onward.

Thirty-six HEALTH records covered uptime 1.2 s to 176 s with Wi-Fi associated;
the clock became synchronized by about 36 s. Internal free heap ranged from
85,235 to 91,279 bytes. The internal minimum watermark was 51,480 bytes at the
first record and settled at 48,136 bytes by 6 s, then did not change for the
remaining ~170 s. The largest internal block was 31,744 bytes in every record,
PSRAM free never fell below 8,364,828 bytes, and the main-task stack minimum
stayed at 2,668 units. The log contains no panic, brownout or error lines.

Limits of this capture: no probes were connected, no HTTP or WebSocket clients
were driving load, and the run was three minutes, so it does not establish a
sustained floor under client load. The normal image does not log LVGL flush
timing: the `LCD_DIAG flush_to_wait_complete_us` event is compiled only when
`CONFIG_MONITOR_LCD_TEST_PATTERN` is set, so no refresh-latency samples were
taken. Optical end-to-end refresh latency still needs a camera or visual
measurement. T04-03 therefore stays open.

## Addendum 2026-11-04 (second capture) — flush diagnostic and unauthenticated HTTP load (T04-03)

A new `CONFIG_MONITOR_LCD_FLUSH_DIAG` option (default off) enables the existing
`LCD_DIAG flush_to_wait_complete_us` log on the normal UI without the test
pattern. A diagnostic image built with it (separate build directory and
sdkconfig, ESP-IDF v6.1) was flashed with a plain `idf.py flash`, then
`tools/device_smoke.py` captured 190 seconds from the reset while four client
threads sent `GET /api/v1/status` over Wi-Fi for 150 seconds, starting about
eight seconds into the capture. 1,486 requests all returned 401; the endpoint
requires authentication and no administrator credentials were used, so this
load exercised the HTTP server and network stack but not authenticated JSON
responses or WebSocket streaming. Client latency was p50 0.216 s, p95 1.401 s,
max 4.941 s (idle single-request latency measured earlier: about 0.03–0.05 s).
There were no timeouts, resets after the initial one, panic, brownout or error
lines. The normal image was restored and passed a 20-second smoke afterwards.

Heap: the internal minimum watermark fell from 51,236 to 47,968 bytes by 6 s, to
41,480 bytes by 11 s and to 41,296 bytes by 16 s of uptime, then did not change
for the remaining ~170 s. This floor is lower than the idle capture (48,136
bytes) and is not distinguishable from boot-time allocation, because the load
began during boot. Free internal heap ranged 76,107–91,199 bytes, the largest
internal block stayed at 31,744 bytes, PSRAM free never fell below 8,364,540
bytes and the main-task stack minimum stayed at 2,668 units.

Flush timing: sixteen samples were logged. The eleven from the initial render
burst (uptime 2.0–2.3 s) ranged 4.9–68.0 ms. The remaining five (4.86 s, 18.7
ms, 14.98 s, 59.97 s, 60.01 s) are not latencies: LVGL emits the flush-wait
event at the next flush, so the interval ends at the next repaint of this
event-driven UI (about once a minute for the clock). The diagnostic is therefore
valid only for back-to-back flushes. Software SPI-transfer timing from the
initial burst is the only usable result; optical end-to-end refresh latency is
still unmeasured, and an accurate steady-state timing would need to hook the
panel transfer-done callback rather than LVGL's wait events.

T04-03 therefore remains open: the memory floor under authenticated API and
WebSocket load, and optical refresh latency, are not measured.

## Addendum 2026-11-04 (third capture) — SPI transfer-complete timing and load (T04-03)

The flush diagnostic from the previous addendum measured the wrong interval, so
`CONFIG_MONITOR_LCD_FLUSH_DIAG` now replaces `esp_lvgl_port`'s transfer-done
callback (which only calls `lv_display_flush_ready()`) with an equivalent one
that timestamps completion first, and logs `LCD_DIAG flush_us` (cumulative
count/min/avg/max of LVGL flush start to SPI transfer complete) every ten
seconds. The diagnostic image was built in a separate build directory and
sdkconfig, flashed with a plain `idf.py flash`, and captured for 190 seconds
with `tools/device_smoke.py`. Starting 62 seconds into the capture, four threads
sent `GET /api/v1/status` over Wi-Fi for 90 seconds (4,160 requests, all 401,
unauthenticated; p50 0.027 s, p95 0.050 s, max 4.317 s). The normal image was
restored afterwards and passed a 20-second smoke without diagnostic output.

Transfer timing: 16 flushes of one 128 × 40 RGB565 strip (10,240 bytes at 20 MHz
SPI, 4.1 ms of raw bus time) were logged, 13 in the first ten seconds and only
three more in the remaining 180 s because the UI repaints only on change.
Cumulative minimum 1.208 ms, average 3.479 ms, maximum 5.180 ms. The maximum
(5.180 ms) was set during the initial render, before any load, and did not
increase while the HTTP load ran; only three flushes occurred during the load
window, so this says little about contention. A full 128 × 160 frame is four
strips, so its transfer time is roughly 5-21 ms (computed from the strip
figures, not measured). This is software timing of the bus transfer; it is not
the panel's optical response and not LVGL render time.

Heap: the internal minimum watermark was 51,404 bytes at the first record,
45,364 bytes from 6.1 s, and fell to 40,408 bytes at 66.1 s, immediately after
the HTTP load began, then held for the rest of the run. Free internal heap
ranged 81,111-91,195 bytes, the largest internal block stayed at 31,744 bytes,
PSRAM free never fell below 8,364,540 bytes, and the main-task stack minimum
stayed at 2,668 units. There were no panic, brownout or error lines and no
resets after the first. The floor under authenticated API and WebSocket load,
and optical refresh latency, remain unmeasured, so T04-03 stays open.

## Addendum 2026-11-04 (fourth capture) — whole-frame update latency (T04-03)

`CONFIG_MONITOR_LCD_FLUSH_DIAG` now also logs whole-frame timing: from the first
strip's flush start to the last strip's SPI transfer completion
(`lv_display_flush_is_last`), cumulative and as an interval maximum that resets
at each ten-second log line. A diagnostic image (flush diagnostic and sensor bus
enabled, saved settings unchanged: Fahrenheit, `extended` mode, 20 s Overview and
10 s Trends dwell, one real probe) was flashed with a plain `idf.py flash` and
captured for 150 seconds; the normal image was restored and smoke-tested after.

Results (software timing from the LVGL flush path; the panel's optical response
is not measured):
- Full-screen switch to Trends: 20.4-21.2 ms per frame (interval maxima at
  23, 53, 83, 113 and 143 s), four 128 × 40 strips.
- Full-screen switch to Overview: 41.3-42.8 ms per frame (interval maxima at
  33, 63, 93 and 123 s).
- First render after boot: 149-171 ms (two captures).
- Steady Overview with unchanged data: interval maximum 0, i.e. no flushes.
- Single-strip SPI transfers 1.17-5.2 ms; the earlier cumulative 983 ms strip
  maximum was a start-timestamp artifact from a transfer completing before the
  first flush-start event and is not a latency.

Observation, not resolved: while Trends is shown the board produced about 78
small flushes per 10-second window (about 8 per second, average frame 3-5 ms)
although the displayed data did not change, whereas the headless display test
asserts zero invalidations for repeated static Trends renders. The source of
these board-side repaints has not been identified; they cost about 3% of SPI
time and cause no visible fault, but they differ from the event-driven repaint
described in T04-12.

Taken with the earlier addenda (two 128 × 40 PSRAM/DMA buffers, lock-protected
updates, idle and authenticated-load memory floors of 48,136 and 39,964 bytes,
no panic), the software-side T04-03 measurements are complete.

## Addendum 2026-11-04 (fifth capture) — Trends repaint cause and fix (T04-12, T04-03)

The unexplained Trends repaints noted in the fourth addendum were traced with the
flush diagnostic extended to log invalidated areas (`LCD_DIAG inval ...`, every ten
seconds, under the LVGL lock). During a Trends window the region
x=0..127, y=119..139 (the compact Trends status line) was invalidated 226 times in
ten seconds, plus a narrow strip about 75 times; steady Overview had none.

Cause: `DisplayView::render()` first set the Trends status label to the row's status
(empty for a healthy probe) and later in the same call overwrote it with `NO DATA`
when the probe had no trend history. The next 100 ms refresh reset it to empty
before overwriting it again, so the label changed twice per refresh. This occurred
only while a healthy probe had no trend data, that is for the first minutes after
boot because the trend cache is RAM-only and starts empty, so the headless tests
(populated cache) did not show it.

Fix: the Trends status text is now computed after the chart data is known and set
once per render. A new headless regression (healthy probe, empty trend cache,
refresh between renders) failed before the fix and passes after it. While writing
it, the existing "no repaint" checks were found to be vacuous: they counted
`LV_EVENT_INVALIDATE_AREA`, which LVGL does not send in the headless display's
full-render mode, so they now count `LV_EVENT_REFR_REQUEST`, include a sanity check
that a forced invalidation is seen, and still pass. Simulation screenshots are
unchanged (byte-identical).

On the board with the fix, the frame count rose by 1-2 per Trends window instead of
about 78-81, and the screen-switch frame times were unchanged (about 20 ms to
Trends, about 42 ms to Overview). The normal image was restored and smoke-tested.
